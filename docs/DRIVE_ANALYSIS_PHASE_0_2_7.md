# 0.2.7 走行解析フェーズへの移行

## 結論

RP8実車で、以下を確認済みです。

- KW905 BLE接続とELM327初期化
- 29-bit header設定（ATCP18 + ATSH...）
- functional OBD要求に対する5つの応答CAN ID
- ECU識別値01へのphysical requestとDID 2012 positive response
- RPM / 車速 / 水温 / 019A / 222012 の継続取得
- RAW保存、SQLite、Offline Replay

このため、次は「走行状態を変えながら既知の安全な診断要求への応答を収集し、状態別に比較する」フェーズへ進める。

## 「全部の応答データ」の意味

このアプリでいう「全応答」は、アプリが送信した診断要求に対してKW905/ELM327が返したすべての応答CAN IDを指す。

対象例:

- 010C RPM
- 010D 車速
- 0105 冷却水温
- 019A Honda Hybrid/EV raw
- 222012 Honda DID 2012 raw

functional要求に複数ECUが応答した場合、それぞれのCAN IDのRAW応答を保存する。

これは「車内CANバス上を流れる全フレームの受動キャプチャ」とは異なる。後者を行うには、ELM327の診断応答方式ではなく、CANable/USB-CAN等の直接CANインターフェースを別途使用する設計が必要。

## 0.2.7で追加した走行後解析の入口

ECU確認ページの保存済み解析に、診断応答インベントリを追加した。

CAN ID × 診断要求ごとに以下を表示する。

- サンプル数
- 異なるpayload数
- payload長
- 変化したByte数

これにより、走行後に「どのECU/要求のデータがよく変化したか」を優先順位付けできる。

## 最初の走行ログで推奨する状態

運転者はMacを操作しない。助手席の人がマーカーを付ける。

1. STOP: READY、完全停止
2. EV: エンジン停止の低速走行
3. ACCEL: 安全な範囲で加速
4. ENGINE ON: エンジン始動状態
5. CRUISE: 一定速度
6. REGEN: 減速・回生
7. STOP: 再び完全停止

各状態を数秒以上維持し、可能なら同じ状態を複数回作る。未知信号の意味は1回の相関だけで確定しない。

## 走行中に行わないこと

- DID範囲スキャン
- ECU総当たり探索
- 書込み系UDSサービス
- ELM327端末から未知コマンド送信
- 運転者本人によるMac操作

走行中は既知のread-only pollingとマーカー記録だけに限定する。
