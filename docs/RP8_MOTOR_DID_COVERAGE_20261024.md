## 重要なブロッカー

過去の Session16 のECU `0E` に約60個のcomplete positive DID、ECU `EF` に `C000`/`C020` のcomplete positive DIDがあったが、今回 M5CAN ではECU01のみサンプリング。M5CAN protocol 1.1/古い物理宛先制限、v1.2 `TX=OFF` の現状では、単にiPad側のECU表示を増やしても取得できない。**車両への許可外TXを開放して解決しない。** Adapter #33 の allowlist・能力交渉・Flow Control帰属・1 outstanding・TX停止・ベンチ試験が前提。

## 実装と検証の進め方

1. **Gate A（直ちに可能、オフライン）**: セッション毎のECU/DID coverage、complete/partial、reference freshness、p50/p95 gap、plan-vs-actualをテスト付きで自動出力。未取得、ECUアダプタ拒否、真のUDS NRC、単なる定数を明確に分ける。元DBは読み取り専用。
2. **Gate B（既知DIDの停車サンプル）**: オーナー/運転者が安全にPレンジ・車速0を確認した後、許可済み完全Positive DIDのみの短いサンプルを新しい記録に保存する設計を追加。停車から動き出したら即停止。速度不明時停止。**交差点0km/hで自動再開禁止**。iPad・M5CANの能力上限を超えない。
3. **Gate C（多ECU・車両TXは保留）**: Adapter #33 に沿いホワイトリスト＆明示opt-in、誤ECUレスポンダ混在時reject、ISO-TP長応答とFlow Controlの安全性、BLE disconnect時TX=OFFを合成テスト→ベンチ試験→駐車Pでの実車試験の順に検証。ユーザーの実車許可前には本番TXしない。
4. **Gate D（自然な走行ログ）**: 同乗者による記録でEV走行/エンジンON/定速/減速回生/停車を包含した独立2回以上のセッションを取る。未探索DID送信は走行中禁止。速度変化に対するRPM比例、停車でのゼロ点、エンジンRPMとの独立性、signedness、時間ラグ、物理量換算をクロス検証。
5. **Gate E（採用）**: Manufacturer文書または別セッションの整合的な物理証拠が揃うまで状態を `UNKNOWN` / `CANDIDATE` と表示し、SmartRingへの表示用確定信号として輸出しない。

## セーフティ／受入条件

- Gate Aは車両TXも製品側の未知探索も増やさず、Linux/macOSの合成SQLiteでテスト可能。
- 一件の高い相関、DID番号近接、他車種の計算式だけで信号名を確定しない。
- `0E/EF` のDID未取得を `UNSUPPORTED` と報告しない。
- CAN/ELMアダプターが未承認なら ECU01以外への物理UDS22 TXは 0件。
- 原SQLiteは公開repoに追加しない。検証・変更は隔離PRで、main直接書込みや自動マージは行わない。
